## 2. Формализация: Что значит «свернуть дерево»?

### 2.1. Формальное математическое определение
Пусть деталь задана графом панелей $\mathcal{G} = (\mathcal{P}, \mathcal{B})$, где:
- $\mathcal{P} = \{P_1, P_2, \dots, P_n\}$ — множество плоских граней/панелей на развёртке;
- $\mathcal{B} = \{B_1, B_2, \dots, B_m\}$ — множество ребер-гибов, где каждый гиб $B_k = (P_i, P_j)$ соединяет смежные панели.
- $P_{ref} \in \mathcal{P}$ — базовая неподвижная панель (reference panel, обычно хаб с максимальной степенью).

Граф $\mathcal{G}$ является деревом (связным ациклическим графом).
Удаление любого ребра $B_k = (P_{parent}, P_{child})$ разбивает дерево $\mathcal{G}$ ровно на две связные компоненты:
$$\mathcal{G} \setminus \{B_k\} = \mathcal{T}_{fixed}(B_k) \cup \mathcal{T}_{moving}(B_k)$$

где:
- $\mathcal{T}_{fixed}(B_k)$ — компонента связности, содержащая базовую панель детали $P_{ref}$ (а следовательно, и родительскую панель $P_{parent}$ относительно направления от корня);
- $\mathcal{T}_{moving}(B_k)$ — поддерево, содержащее дочернюю панель $P_{child}$ и все её дочерние ветви.

**«Свернуть дерево»** означает:
При выполнении сгиба по линии $B_k$ пространственная трансформация жесткого тела (Rigid Body Transformation) $\mathbf{T}_{B_k}$ (состоящая из трансляции нейтрального слоя и вращения Родригеса на угол $\theta_k$ вокруг локальной оси гиба) применяется **ко всем телам и граням поддерева $\mathcal{T}_{moving}(B_k)$ как к единому кинематическому целому**, в то время как панели поддерева $\mathcal{T}_{fixed}(B_k)$ остаются строго неподвижными.
Между стыкуемыми панелями $P_{parent}$ и $P_{child}$ вшивается канонический цилиндрический сектор гиба $S_{bend}(B_k)$, торцы которого канонизируются методом `_canonicalize_bend_sector`.

### 2.2. Подтверждение на конкретной фикстуре (`sqin_200_25_10_ok`)
Рассмотрим фикстуру `sqin_200_25_10_ok` (9 панелей, 8 гибов):
- Базовый хаб: $P_0 = \text{PANEL\_b055c460}$ (дно $200 \times 200$ мм, $\deg = 4$).
- 4 боковые стенки: $P_{s1}, P_{s2}, P_{s3}, P_{s4}$ соединены с $P_0$ гибами первого уровня $B_1, B_2, B_3, B_4$.
- 4 концевые отбортовки: $P_{f1}, P_{f2}, P_{f3}, P_{f4}$ соединены со стенками гибами второго уровня $B_5, B_6, B_7, B_8$.

Поведение кинематики:
1. **При сгибе второго уровня (гиб $B_5$ между стенкой $P_{s1}$ и фланцем $P_{f1}$):**
   - Удаление $B_5$ делит граф на:
     - $\mathcal{T}_{fixed}(B_5) = \{P_0, P_{s1}, P_{s2}, P_{s3}, P_{s4}, P_{f2}, P_{f3}, P_{f4}\}$
     - $\mathcal{T}_{moving}(B_5) = \{P_{f1}\}$
   - Трансформация вращает ровно 1 панель $P_{f1}$.
2. **При сгибе первого уровня (гиб $B_1$ между хабом $P_0$ и стенкой $P_{s1}$):**
   - Удаление $B_1$ делит граф на:
     - $\mathcal{T}_{fixed}(B_1) = \{P_0, P_{s2}, P_{s3}, P_{s4}, P_{f2}, P_{f3}, P_{f4}\}$
     - $\mathcal{T}_{moving}(B_1) = \{P_{s1}, P_{f1}\}$
   - **Критическое отличие от линейной цепочки:** Трансформация сгиба $B_1$ должна поворачивать **не только смежную стенку $P_{s1}$, но и подвешенный к ней фланец $P_{f1}$**, даже если фланец уже был изогнут на предыдущем шаге или ещё плоский!

## 3. Алгоритм построения `moving_panels`

Множество `moving_panels` для каждого гиба вычисляется детерминированно из топологического графа деталей:

```text
               [P_hub] (Reference Root)
              /   |   \   \
          B_1/ B_2| B_3\   \B_4
            /     |     \   \
        [P_s1]  [P_s2] [P_s3] [P_s4]
          |       |      |      |
       B_5|    B_6|   B_7|   B_8|
          v       v      v      v
        [P_f1]  [P_f2] [P_f3] [P_f4]
```

### 3.1. Алгоритм обхода (BFS / DFS):
1. **Инициализация корня:** Корень дерева $P_{root} = P_{ref} = \text{canonical\_part.payload.reference\_panel\_id}$. Если $P_{ref}$ не задан, корнем выбирается первая панель с максимальной степенью ($\deg \ge 3$).
2. **Ориентация рёбер:** Для каждого ребра $B_k = (P_a, P_b)$ определяется направление «родитель $\to$ потомок» относительно $P_{root}$ (родитель лежит на кратчайшем пути от $P_{root}$ к гибy).
3. **Изоляция поддерева:**
   Для целевого гиба $B_k = (P_{parent}, P_{child})$:
   - Инициализируем очередь: $Q = [P_{child}]$, $\mathcal{M} = \{P_{child}\}$.
   - Пока $Q$ не пуста, извлекаем панель $u = Q.pop()$.
   - Для каждого соседа $v \in \text{adj}(u)$:
     - Если ребро $(u, v) == B_k$ (то есть возврат к родителю $P_{parent}$): переход блокируется.
     - Иначе, если $v \notin \mathcal{M}$: добавляем $v$ в $\mathcal{M}$ и помещаем $v$ в очередь $Q$.
4. **Результат:** $\mathcal{T}_{moving}(B_k) = \mathcal{M}$.
   - Дополнительная проверка инварианта: $\mathcal{T}_{moving}(B_k) \cap \mathcal{T}_{fixed}(B_k) = \emptyset$ и $P_{root} \notin \mathcal{T}_{moving}(B_k)$.

## 4. Критерии верификации и топологической валидации

### Меняется ли критерий `topology_matches` из Task 1.0.1b-2-fix-2/3?
**Нет. Критерий валидации не меняется.**

Эталонная архитектура SMBS основана на принципе инвариантности контроля качества:
- Контролер `BaselineWorker.compare_topologies` остаётся независимым судьёй.
- Меняется исключительно внутренний способ построения геометрии в `SheetMetalFolder.fold_tree_from_flat_pattern` (применение преобразований к поддеревьям вместо линейной цепочки).

Свернутая деталь считается валидной (`baseline_status == "VALID"`), если:
1. `counts_match == True` (совпадают счётчики плоских, цилиндрических и прочих граней);
2. `sum_areas_match == True` (совпадают суммарные площади поверхности);
3. `plane_areas_match == True` и `cyl_areas_match == True` (совпадают отсортированные площади с допуском $10^{-2}\,\text{мм}^2$);
4. `normals_match == True` (попарное совпадение знаковых нормалей $\vec{n}_{ref} \cdot \vec{n}_{rest} \ge \cos(0.5^\circ)$ и позиций плоскостей относительно центроида детали $|pos_{ref} - pos_{rest}| \le 0.1\,\text{мм}$).

## 5. Обработка неоднозначностей (Ambiguities)

Принцип SMBS: **«Никаких эвристических догадок. Неоднозначность = диагностика и отказ»**.

### Возможные ситуации неоднозначности:
1. **Циклический граф (Cyclic Graph / Closed Loops):**
   Если при обходе ребро ведёт в уже посещённую вершину не через прямого родителя (наличие замкнутого контура в развёртке), то деталь не является деревом.
   - *Действие:* Немедленный отказ с диагностикой `NON_TREE_TOPOLOGY: cyclic panel graph detected`.
2. **Несвязный граф (Disconnected Graph / Forests):**
   Если часть панелей недостижима из $P_{root}$ через гибы.
   - *Действие:* `DISCONNECTED_PANEL_GRAPH: unreachable panels detected`.
3. **Неопределённость базовой панели при равнозначных хабах:**
   Если в детали несколько панелей имеют одинаковую максимальную степень (например, два хаба со степенью 3, соединённые между собой) и в `canonical_part` не задан `reference_panel_id`.
   - *Действие:* В соответствии с правилом задачи фиксируется статус:
     `code = "AMBIGUOUS_TOPOLOGY_ROOT"`
     `level = "ERROR"`
     `baseline_status = "INVALID"` (или `UNKNOWN`).
     Никакого «угадывания» или случайного выбора корня.

## 6. Симметрия детали: Декларативное описание в канонической модели

### 6.1. Обратная совместимость и архитектура симметрий в 3a
В `BaselineWorker` реализуется строгая обратная совместимость:
1. **Если `symmetry_transformations` отсутствует в `canonical_part`:** `BaselineWorker` использует текущий проверенный дефолтный список преобразований (identity $\mathcal{R}_0$ + повороты на $180^\circ$ вокруг главных осей $X, Y, Z$). Это гарантирует, что все существующие 7 фикстур (и 219 тестов репозитория) продолжают проходить без малейших изменений.
2. **Если `symmetry_transformations` задан в `canonical_part`:** `BaselineWorker` использует **исключительно** указанный список допустимых симметрий для данной детали.

### 6.2. Расширение канонической схемы `canonical_part.schema.json`
Поле `payload.symmetry_transformations` добавляется в схему как **опциональное**:
```json
"symmetry_transformations": {
  "type": "array",
  "items": {
    "type": "object",
    "required": ["type", "axis", "angle_deg"],
    "properties": {
      "type": {"type": "string", "enum": ["ROTATION", "REFLECTION"]},
      "axis": {"type": "array", "items": {"type": "number"}, "minItems": 3, "maxItems": 3},
      "origin": {"type": "array", "items": {"type": "number"}, "minItems": 3, "maxItems": 3},
      "angle_deg": {"type": "number"}

  }
}
```

### 6.3. Known Limitation: Автоопределение симметрий
В рамках этапа 3a автоопределение группы симметрий из геометрии не реализуется, чтобы не усложнять задачу и исключить эвристические риски. Схема расширяется опциональным полем, дефолт полностью обратно совместим. Автоматическое вычисление группы симметрий детали выносится в отдельную задачу этапа Stage 2 (Canonical Part Analyzer).

## 7. Согласование с ТЗ §6.2: Проверка коммутативности операций гибки

В теории кинематики развёртки независимые ветви дерева должны сворачиваться коммутативно. Однако ТЗ §6.2 категорически запрещает априорно предполагать коммутативность:
$$\mathbf{T}_i(\mathbf{T}_j(\mathcal{S})) \stackrel{?}{=} \mathbf{T}_j(\mathbf{T}_i(\mathcal{S}))$$

### 7.1. Когда гибы обязаны коммутировать:
Гибы $B_i$ и $B_j$ принадлежат **разным ветвям дерева**, исходящим из одного родительского узла:
$$\mathcal{T}_{moving}(B_i) \cap \mathcal{T}_{moving}(B_j) = \emptyset$$
Их линии сгиба не пересекаются, и перемещаемые ими множества тел не зависят друг от друга.

### 7.2. Когда гибы не коммутируют:
Гиб $B_j$ является потомком гиба $B_i$:
$$B_j \in \mathcal{T}_{moving}(B_i) \implies \mathcal{T}_{moving}(B_j) \subset \mathcal{T}_{moving}(B_i)$$
В этом случае сначала должен выполняться гиб $B_j$ относительно исходной системы координат ветви, либо при прямом сворачивании от корня позиция оси $B_j$ должна пересчитываться трансформацией $\mathbf{T}_{B_i}$.

### 7.3. Процедура численной верификации коммутативности (§6.2):
Для любых двух независимых гибов $B_1$ и $B_2$:
1. Строится промежуточное тело $\mathcal{S}_{12} = \text{fold}(B_2, \text{fold}(B_1, \mathcal{S}_{flat}))$.
2. Строится альтернативное тело $\mathcal{S}_{21} = \text{fold}(B_1, \text{fold}(B_2, \mathcal{S}_{flat}))$.
3. Вычисляется отклонение формы по реалистичным инженерным допускам:
   - Относительное отклонение объёма:
     $$\frac{|\Delta V|}{V_{nom}} = \frac{|V(\mathcal{S}_{12}) - V(\mathcal{S}_{21})|}{V_{nom}} < 10^{-6}$$
   - Смещение центра масс:
     $$\|\Delta \mathbf{c}\| = \|\mathbf{c}(\mathcal{S}_{12}) - \mathbf{c}(\mathcal{S}_{21})\| < 10^{-2}\,\text{мм}$$
Если отклонение превышает допуск, операция признаётся **некоммутативной** с обязательной фиксацией строгого порядка в графе технологических переходов.
## 8. План реализации этапа 3a

### 8.1. Изолированная архитектура fold
- Существующий метод `fold_multi_bend_from_flat_pattern` **остаётся нетронутым** во избежание регрессий на 1D линейных цепочках (Stage 1).
- Создаётся новая изолированная функция:
  `SheetMetalFolder.fold_tree_from_flat_pattern(flat_pattern, canonical_part) -> Part.Shape`
  (в текущей версии 3a: специализированная реализация для сбалансированной 4-лучевой ортогональной топологии; обобщённый BFS/DFS-подход — Known Limitation для 3c).
- В точке входа `fold_from_canonical_part` внедряется диспетчер (switch) по типу графа:
  - Если топология 1D линейная (`max_deg <= 2` и `len(leaves) == 2`) $\to$ вызывается проверенный `fold_multi_bend_from_flat_pattern`.
  - Если топология древовидная (`max_deg >= 3` и граф ацикличен) $\to$ вызывается новый `fold_tree_from_flat_pattern`.
  - Иначе $\to$ возбуждается явный отказ с диагностикой (`NON_TREE_TOPOLOGY` или `AMBIGUOUS`).

### 8.2. Порядок выполнения реализации Фазы 2:
1. **Реализация `fold_tree_from_flat_pattern` в `sheetmetal_folder.py`:**
   - Построение ориентированного дерева панелей от базового хаба `reference_panel_id`.
   - Определение `moving_subtree` для каждого гиба через BFS/DFS.
   - Изоляция ветвей, вырезание секторов гибов из развертки, генерация канонических гибочных твердотельных секторов через `bend_solid` + `_canonicalize_bend_sector`.
   - Применение преобразований жесткого тела к перемещаемым поддеревьям.
   - Сшивка и финальное объединение через `ShapeUpgrade_UnifySameDomain`.
2. **Тестирование 4 целевых древовидных фикстур:**
   Создание постоянного теста `tests/test_baseline_topology_tree.py` для:
   - `sqin_200_25_10_ok`
   - `sqout_200_25_10_ok`
   - `box_100out_50in_ok`
   - `box_100in_50out_false`
   Проверка `topology_matches == True` и `baseline_status == "VALID"`.
3. **Регрессионный прогон всех существующих тестов:**
   Гарантия 0 новых ошибок по сравнению с `BASELINE_FAILURES_AFTER.md`.
